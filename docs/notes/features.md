# Planned Features

## 1. Adjustable dose time after logging
Right now pressing "Take dose" stamps the dose with the current time and that's final. Instead, after logging a dose there should be a way to go back and correct *when it was actually taken* — e.g. tapping the existing edit icon (✎) next to the "Taken at" time on the Today page should open a small time picker rather than being purely decorative. Saving a correction should update the release curve, the timeline milestones, and the "Logged at HH:MM · N min after taking" flag so they all reflect the corrected time rather than the original log time. This matters because people often log a dose a few minutes (or longer) after actually taking it, and the curve's accuracy depends on the real taken-time, not the click time.

**Implementation notes:** The `tracker` app currently has no real `Dose` model (just the scaffold `TodoItem`), so this is also where the first real model gets added — `Dose(user, medication, scheduled_at, taken_at, logged_at, status)`. Add a DRF endpoint (e.g. `PATCH /doses/<id>/`) that only allows updating `taken_at`, leaving `logged_at` alone as an audit trail of when the correction happened. On the frontend, replace the decorative `.edit-icon` span in [Today.vue](frontend/src/views/user/Today.vue) with a click handler that opens a small time-picker (a lightweight modal/popover component, no need for a full form library), calls a new `updateDoseTime(doseId, time)` in [api.js](frontend/src/api.js), and on success refetches/recomputes `dose`, `timeline`, and `curvePath` so everything derived from `taken_at` shifts together. If `taken_at` ends up differing from the original logged time, flip the day's status to `edited` (the status value already exists in `STATUS_LABELS`).

## 2. Notes overlaid on the release curve
The release curve chart (on Today, and reused in History) should render the day's notes as markers positioned at the time they were logged, not just list them in a separate sidebar. Hovering/tapping a marker would show the note text, and flagged notes (e.g. "crashed hard at 4") should be visually distinct (e.g. a red marker vs. a neutral one) so patterns between the curve shape and how the person felt are visible at a glance. This should work identically in two places:
- **Today page** — overlaying today's notes on the live curve as they're added.
- **History page, per-day view** — clicking a specific day in the history list should open that day's curve with that day's notes overlaid on it, so past days are reviewable the same way as today.

**Implementation notes:** The curve is currently drawn inline inside [Today.vue](frontend/src/views/user/Today.vue) as a raw `<svg>` block — the first step is pulling that into a shared `CurveChart.vue` component that takes `curvePath` and a `notes` array as props, so Today and History can both use it instead of duplicating the markup. Add a helper in [curve.js](frontend/src/lib/curve.js) that maps a note's clock time to an x-coordinate using the same 6am–12am → 34–890 scale already used for the axis labels, then render one marker (`<circle>` or small `<g>`) per note on top of the `<path>`, styled differently for `flagged` notes, with a hover/tap tooltip showing the note text. For the History side, add a per-day route (e.g. `/history/:date`) and a matching backend endpoint (e.g. `GET /days/<date>/` returning that day's dose, curve inputs, and notes in one payload) so the per-day view can fetch and render everything in a single call.

## 3. Aggregate stats on the History root page
The History page currently just lists individual days. Before drilling into a specific day, the root History view should surface summary stats across the visible date range (e.g. last 30 days, or a selectable range) — things like:
- Average time from scheduled dose to actual taken time (adherence/lateness trend)
- % of days on-time vs. late vs. missed
- Average / most common "crash" time reported in notes
- Streaks (e.g. current on-time streak, longest streak)

This gives an at-a-glance view of patterns over time instead of requiring the person to open each day individually and mentally aggregate.

**Implementation notes:** [History.vue](frontend/src/views/user/History.vue) is currently just a stub (`<p>History</p>`) backed by static `HISTORY_SEED` data, so this is where it becomes a real page. Add a stats endpoint (e.g. `GET /doses/stats/?range=30d`) computed with Django ORM aggregates (`Count`, `Avg` on `taken_at - scheduled_at`) plus a small Python loop for streaks, since window functions for consecutive-day streaks are fiddly to express purely in the ORM. On the frontend, replace `HISTORY_SEED` with a real fetch to the day-list endpoint, add a `range` selector (defaulting to last 30 days), and render a stats row/cards above the existing list using the stats response — this is a good point to also introduce a Pinia store or composable (e.g. `useHistory()`) since Today, History root, and the per-day view from #2 will all want overlapping dose/note data.

## 4. LLM-generated summary of the history stats
Once the aggregate stats from #3 exist, add a short natural-language summary generated from them — a few sentences, not a wall of text — e.g. "You've been on-time 8 of the last 10 days. Afternoon crashes around 4pm show up in your notes 3 times this week, usually 5-6 hours after your dose." This sits alongside the stats block on the History root page and should be regenerated whenever the underlying date range/stats change, not recomputed on every render.

**Implementation notes:** This needs a server-side LLM call — never call the Anthropic API directly from the Vue frontend, since that would expose the API key. Add a small summarisation module in the backend (e.g. `tracker/summaries.py`) that takes the stats payload from #3, builds a prompt from it, and calls the Claude API (Messages API, a small/fast model is enough for a few sentences), exposed via `POST /summaries/history/`. Store the result in a `Summary(user, kind, range_key, text, generated_at)` model keyed by the date range so it's cached rather than regenerated on every page load — invalidate/regenerate it only when a new dose or note is logged inside that range, or once a day. The frontend just fetches the cached text alongside the stats call and shows a loading/placeholder state while a fresh one is generating.

## 5. LLM-generated summary for a single day
The same summarisation approach as #4, applied at the individual-day level: when viewing a specific day in History (see #2), show a short generated summary of how that day went — combining the curve shape, dose timing, and that day's notes into a few sentences (e.g. "Dose taken 15 minutes late. You reported a slow start until mid-morning, followed by a good, steady afternoon with no flagged notes."). This is scoped to a single day's data rather than the multi-day trends in #4.

**Implementation notes:** Reuse the summarisation module from #4 with a second prompt template and a different input shape — the day's dose timing, curve, and notes list (the same payload the per-day view in #2 already fetches) instead of aggregate stats. Add `POST /summaries/day/?date=...`, cached the same way (a `Summary` row with `kind='day'`, keyed by date, regenerated only if that day's notes or dose are edited after the fact). Surface the text in the per-day History view built for #2, near the curve/notes overlay.

## 6. LLM-assisted predictions on the Today page
Extend the same LLM summarisation to the Today page, using the current day's release curve to suggest good windows for things like eating and focused work — e.g. "Peak effect is expected around 11am–1pm; consider scheduling demanding work then" or "Effect is tapering after 5pm, a good window for dinner." This is a suggestion, not a scheduling feature, and should be clearly framed as a prediction based on the modelled curve rather than a measurement.

As a future extension, allow logging additional stimulants (caffeine, nicotine) with a dose amount (mg), so their effect can be modelled alongside the primary medication and factored into the curve and the predictions above. This would need its own release-curve model per substance and a way to combine/overlay multiple curves.

**Implementation notes:** Same summarisation module again, third prompt variant (`POST /summaries/today/`), fed the current curve shape and current time-of-day rather than historical data — cache per day and regenerate once (or on a manual "refresh" action), not on every page load, since [Today.vue](frontend/src/views/user/Today.vue) re-renders often. Render the returned text near the existing `.chart-caption`. For the stimulant extension: add a `Substance` reference table (name, default release-curve shape) and a `StimulantDose(user, substance, mg, taken_at)` model, loggable from a small form on Today; extend [curve.js](frontend/src/lib/curve.js) with a per-substance curve function scaled by `mg` (similar to how `dayCurvePath` already scales `DAY_CURVE_BASE_POINTS`), and decide on a combination rule (simplest: sum the curves, clamped to 100%) before rendering the extra curve(s) as additional `<path>` elements in `CurveChart.vue`. The prediction prompt in #6 then just includes these extra doses as additional context alongside the primary medication's curve.
